# Procurement RAG Legal Checker

Система проверки комплектов российской закупочной документации. Она извлекает данные из документов, сопоставляет их между собой и проверяет расчёты и отдельные нормативные требования. Результат доступен в веб-интерфейсе и в скачиваемом Word-отчёте.

Проект активно разрабатывается. Покрытие правил зависит от состава и формата документов; результат требует оценки специалистом и не является гарантией юридической корректности закупки.

## Возможности

- Сверка наименований, кодов, количества, единиц измерения, сроков, адресов, гарантий и этапов исполнения между документами.
- Проверка ОНМЦК: арифметика строк и итогов, цены поставщиков, минимальные цены, коэффициент вариации, расчёты товаров и услуг внутри этапов.
- Извлечение коммерческих предложений (КП), сопоставление с ОНМЦК и проверка цен, реквизитов, количества и единиц.
- Сверка наименований ОКПД2 с локальным официальным справочником и проверка национального режима по локальным перечням ПП №1875.
- Получение карточек КТРУ с `zakupki.gov.ru`, сверка характеристик и единиц ООЗ, проверка дополнительных характеристик и наличия обоснований.
- Проверки отдельных условий контракта и заявки: обеспечения, дополнительные требования к участникам, СМП/СОНКО, штрафы и пени.
- Ручная и общая загрузка документов с распределением по ролям; полный или сокращённый просмотр отчёта.

Заявка в план-график (ПГ) обязательна и служит основой междокументной сверки, когда содержит нужное значение. Проверки по официальным справочникам оценивают и сами данные ПГ. Остальные документы необязательны, но их отсутствие ограничивает доступные проверки.

### Документы и форматы

| Роль | Форматы рабочего сервиса |
| --- | --- |
| Заявка в план-график, ООЗ, проект контракта, ОНМЦК/ОЦК | DOCX |
| Обращение, пояснительная записка | DOCX, PDF |
| Коммерческие предложения | DOCX, PDF; сервис также обрабатывает PNG, JPG/JPEG и WebP |

PDF и изображения читаются через VLM. Это не универсальная поддержка PDF для всех ролей. Ограничения выбора файлов в интерфейсе и отдельных CLI могут отличаться; подробнее в [руководстве запуска](docs/runtime_guide.md).

## Архитектура и состояние pipeline

Название сохраняет историю RAG-проекта. В текущем пути web/worker нет поиска по векторной базе: обработка опирается на структурированное извлечение, детерминированные проверки и адресные LLM/VLM-вызовы. Функции embeddings остаются в `shared_modules/llm_models.py`, но не вызываются рассмотренными точками входа.

```text
Django: загрузка файлов
  -> Redis: очередь Celery
  -> worker: временные файлы
  -> summary_model.web_service.process_uploaded_documents
     -> DOCX / таблицы -> extract_package -> типизированные схемы
     -> VLM для сложных таблиц и поддерживаемых PDF/изображений
     -> LLM-извлечение и специализированные проверки
     -> детерминированные правила + локальные справочники + live КТРУ
     -> текст отчёта
  -> worker: DOCX + результат задачи
  -> Django: просмотр и скачивание
```

| Путь | Состояние и назначение |
| --- | --- |
| [`summary_model/web_service.py`](summary_model/web_service.py) | Текущий рабочий оркестратор, напрямую вызываемый Celery worker. |
| [`summary_model/full_pipeline_cli.py`](summary_model/full_pipeline_cli.py) | CLI того же оркестратора с JSON-диагностикой. Настройки по умолчанию отличаются от worker. |
| [`summary_model/extraction_pipeline.py`](summary_model/extraction_pipeline.py), [`extraction_cli.py`](summary_model/extraction_cli.py) | Развиваемый слой типизированного извлечения `ProcurementPackageExtraction`. Уже используется внутри рабочего оркестратора; отдельно запускается без проверок и итогового отчёта. |
| [`summary_model/checks_cli.py`](summary_model/checks_cli.py) | Проверки сохранённого JSON-пакета без повторного чтения документов. |
| [`summary_model/service.py`](summary_model/service.py), [`cli.py`](summary_model/cli.py) | Отдельный вариант schema-first pipeline: `DocumentExtractionEngine`, `ProcurementPackage`, analyzers, validation и свой renderer. Не вызывается текущим worker; статус его дальнейшей интеграции по коду не установлен. |
| `summary_model/*_lab/` | Диагностические и экспериментальные инструменты для парсинга, VLM, ОНМЦК, КП и structured output. Некоторые используют рабочие компоненты, но не заменяют полный сервис. |

Выражение «новый pipeline» в исторических планах неоднозначно: слой `extract_package` уже интегрирован, а отдельный путь `service.py` не подключён к текущему worker. [Подробности точек входа и различий](docs/runtime_guide.md#точки-входа).

## Стек

Python 3.12 (Docker), Django 5, Celery 5, Redis 7, Pydantic 2, python-docx, PyMuPDF, Pillow, requests, BeautifulSoup, LangChain/OpenAI SDK и OpenAI-совместимый LLM/VLM-провайдер.

Redis обслуживает очередь задач и хранение результатов Celery. SQLite используется для локального справочника ПП №1875 и стандартной базы Django; официальные наименования ОКПД2 доступны из JSON.

## Быстрый локальный запуск

Нужны Docker с Compose и доступ к совместимому API, который предоставляет используемые модели. Из корня репозитория создайте `web/.env` со своими значениями:

```dotenv
SECRET_KEY=<django-secret-key>
DEBUG=False
ALLOWED_HOSTS=localhost,127.0.0.1
OPENAI_API_KEY=<provider-api-key>
OPENAI_BASE_URL=https://<provider-host>/v1
SUMMARY_WITH_VLM_TABLES=1
```

`SUMMARY_WITH_VLM_TABLES=1` включает обработку сложных DOCX-таблиц через VLM. В worker она по умолчанию выключена; VLM для КП и коротких PDF включена. Доступность моделей необходимо согласовать с провайдером, см. [переменные окружения](docs/runtime_guide.md#переменные-окружения).

```bash
docker compose up --build -d
```

Откройте [http://localhost:8000/](http://localhost:8000/). Для установленного отдельно Compose v1 эквивалентная команда: `docker-compose up --build -d`.

Текущий Compose поднимает Redis, выполняет миграции Django, запускает `runserver` и Celery worker с четырьмя потоками. Он переопределяет `DEBUG=False`, **`ALLOWED_HOSTS="*"`** и адреса Redis независимо от `web/.env`; публикует порты 8000 и 6379. Это описание существующей конфигурации, а не инструкция готового production-развёртывания.

Команды в документации сверены чтением кода и конфигов; в рамках обновления README они не запускались.

## CLI

Запускайте из корня репозитория в окружении с зависимостями из четырёх файлов requirements, перечисленных в [руководстве](docs/runtime_guide.md#зависимости-и-запуск). Redis для CLI не требуется.

Полный прогон через рабочий оркестратор **с внешними LLM/VLM-вызовами**, но без live КТРУ:

```bash
python -m summary_model.full_pipeline_cli --input-dir "doci_primery/<PACK>" --output-dir "runtime/full_pipeline_runs/<RUN>" --no-ktru
```

Только детерминированное извлечение DOCX, без внешних вызовов и проверок:

```bash
python -m summary_model.extraction_cli --input-dir "<DOCX_PACK_DIR>" --output-dir "runtime/extraction_runs/<RUN>"
```

`--no-ktru` не отключает LLM/VLM. Full-pipeline CLI выбирает файлы по именам из одного каталога, берёт один файл большинства ролей и все распознанные КП. Варианты документов нужно разделять; выбор фиксируется в `inputs.json`. Этот CLI сохраняет текст и JSON, но не создаёт Word-отчёт worker.

## Ограничения

- Неоднородные и повреждённые таблицы, сканы и рукописные реквизиты могут извлекаться неполно или неверно. LLM/VLM-ответы не гарантируют повторяемость результата.
- Внешние вызовы отправляют текст или изображения документов провайдеру и могут тарифицироваться. Доступность API и карточек КТРУ влияет на полноту проверки.
- По умолчанию VLM читает до 8 страниц КП и до 4 страниц обращения/пояснительной записки; лимиты настраиваются. Обработка всех страниц длинного PDF не гарантирована.
- Ошибка обязательной ПГ прекращает обработку; ошибки необязательных документов и отдельных внешних проверок могут дать частичный отчёт с предупреждениями.
- Локальные справочники являются подготовленными снимками данных. Их актуальность не подтверждается автоматически каждым запуском.
- Успешное завершение команды не доказывает корректность всех проверок: важны выбранные файлы, извлечённые данные, предупреждения и диагностические артефакты.
