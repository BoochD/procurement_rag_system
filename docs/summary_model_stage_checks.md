# Проверки этапов в новом summary_model

## Источник истины

Заявка в план-график является ground truth для этапов:

- порядок этапов;
- номера этапов;
- сроки поставки / оказания услуг / выполнения работ по этапам;
- признак наличия этапов.

Если в ПГ этапы не предусмотрены, отсутствие этапов в других документах не считается ошибкой.
Если в ПГ этапы есть, ООЗ, проект контракта и ОНМЦК должны быть сверены с ПГ.

## Что проверяется strict-логикой

### Этапы против ПГ

Проверка `strict.plan.stages`:

- сравнивает номера и порядок этапов;
- сравнивает сроки этапов по датам, если даты распознаны;
- если дат нет, сравнивает нормализованный текст срока;
- не проверяет цены этапов.

Статусы:

- `passed`: порядок и сроки согласованы;
- `failed`: найдено прямое расхождение номеров, порядка или сроков;
- `manual_review`: этапы есть, но часть данных не распознана структурированно;
- `passed`: этапы нигде не предусмотрены.

### Стоимость этапов в ОНМЦК

Проверка `strict.onmck.stage_prices`:

- применяется только к `nmck_staged_calculation_table`;
- группирует строки вида `1.1`, `1.2` под этапом `1`;
- сверяет цену этапа с суммой вложенных строк;
- сверяет сумму этапов с итогом ОНМЦК.

Обычная арифметика ОНМЦК и минимальная цена за единицу остаются отдельными проверками.

## LLM fallback

Если deterministic-проверка этапов не прошла, а checks запущены с `--with-llm`, включается маленький fallback:

```text
run_stage_llm_checks(package)
```

LLM получает только уже распарсенные этапы из схем:

- `schedule_application.stages`;
- `purchase_request.stages`;
- `purchase_description.stages`;
- `contract_draft.stages`;
- `nmck_justification.stages`.

LLM не получает полный DOCX и не проверяет цены этапов. Его задача только оценить согласованность порядка и сроков, если deterministic-сравнение оказалось слишком грубым.

Если LLM считает этапы согласованными после failed/manual deterministic, итоговый статус остаётся `warning`, чтобы не скрывать, что применялся semantic fallback.

## Что не делаем сейчас

- Не строим универсальный rule engine для всех возможных таблиц этапов.
- Не пытаемся проверять состав поставки внутри этапа, если он не распознан явно.
- Не проверяем КП/OCR по этапам.
- Не используем VLM, если таблица этапов уже распарсилась deterministic-слоем.
