# Тестирование checks/report без extraction

Цель этого слоя тестов: стабильно проверять поведение проверок и итогового отчёта без повторного парсинга DOCX/PDF, без live LLM, без VLM и без внешних сервисов.

## Источник данных

Для unit-тестов checks/report используем готовые Pydantic-объекты:

- `ProcurementPackageExtraction` для запуска `run_checks(...)`;
- `CheckResult` и `ProcurementChecksReport` для проверки только рендера отчёта.

Документы из `doci_primery/` остаются smoke/manual fixtures. Их не надо читать в обычных unit-тестах отчёта.

## Что обязательно проверять

- порядок крупных секций отчёта соответствует `docs/ideal_report_mockup.md`;
- все пользовательские названия документов выводятся по-русски;
- в финальный `report.txt` не попадают debug-структуры: `raw_rows`, `logical_rows`, `compact_json`, `compact_markdown`;
- этапы выводятся таблицей, а не JSON/list dump;
- КП выводятся отдельным блоком, включая понятный текст для случая “КП не приложены”;
- подробные debug-данные сохраняются в `checks.json`, но не раздувают читаемый отчёт.

## Этапы, КП и VLM fallback

### ОКПД2 для позиций КТРУ

ПГ остаётся эталоном кодов. Если позиция ООЗ содержит только КТРУ, адаптер
характеристик может использовать ОКПД2 из одной однозначно сопоставленной
позиции ПГ: сначала по тому же КТРУ, затем по устойчиво похожему наименованию.
При нескольких кандидатах код не подставляется. В `checks.json` сохраняются
исходный код позиции, код ПГ и источник применённого правила.

### Коммерческие предложения PDF

Для PDF-КП VLM получает одновременно изображения страниц и доступный текстовый
слой PDF. Из текстового слоя детерминированно восстанавливаются явные реквизиты:
поставщик, исходящий номер и дата, итоговая сумма, срок поставки и строки с
иерархическими номерами `1.1`, `1.2`, ... . Если таблица содержит агрегатную
строку `1` и детальные дочерние строки, в `items` входят только дочерние строки.
Результат VLM обогащает этот baseline, но не может удалить восстановленные
числа и реквизиты.

В отчёте сведения о КП показываются двумя компактными таблицами: реквизиты КП
и построчная сверка цен с ОНМЦК. Повторяющиеся технические причины остаются в
`checks.json`, а не разворачиваются в длинный список в Word/HTML.

### Запуск тестов на Windows

Тесты нового checks-слоя используют `TemporaryDirectory`. Если системный
`%TEMP%\pytest-of-<user>` имеет неверного владельца, сначала очистите или
исправьте права на него. Для остальных старых тестов можно использовать
явный workspace-каталог:

```powershell
python -B -m pytest tests\summary_model_tests -q -p no:cacheprovider `
  --basetemp=runtime\pytest_manual
```

Временные файлы тестов не являются runtime-артефактами проверки и могут
удаляться после прогона.

- Этапы передаются из checks в `details.stage_tables` как структурированные
  строки, а не как сериализованный JSON. Итоговый отчёт выводит отдельную
  таблицу для ПГ, ООЗ, проекта контракта и ОНМЦК, если этапы извлечены.
- Для КП отчёт разделяет извлечённые реквизиты, поля, которые VLM не смогла
  определить, и фактически подтверждённые расхождения с ОНМЦК. Неоднозначное
  сопоставление позиции остаётся `manual_review`.
- Ошибки схемы или JSON VLM не должны попадать в пользовательский отчёт со
  стеком и внутренними полями Pydantic. В отчёте показывается короткое
  предупреждение, а точная причина сохраняется в runtime-артефактах и логах.

## Как мокать дорогие этапы

Для CLI/checks тестов дорогие части заменяются monkeypatch:

- `run_semantic_llm_checks(...)`;
- `run_stage_llm_checks(...)`;
- `run_penalty_llm_checks(...)`;
- `run_ktru_characteristic_checks(...)`.

Если тест проверяет только текст отчёта, лучше вообще не вызывать `run_checks(...)`, а собрать минимальный `ProcurementChecksReport` из `CheckResult`.

## Минимальные команды

```powershell
python -B -m pytest tests\summary_model_tests\test_checks_report_rendering.py -q
python -B -m pytest tests\summary_model_tests\test_extraction_checks.py -q
```

Если локальный Python не содержит зависимости проекта, запускать эти команды из активированного `myenv`.
